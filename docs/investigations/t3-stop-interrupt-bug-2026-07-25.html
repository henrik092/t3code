Technischer Untersuchungsbericht

T3 Code konnte einen laufenden Turn nicht stoppen

Untersuchung des Vorfalls vom 25. Juli 2026: Ein laufender Turn nutzte Browser Use im angemeldeten Google Chrome. Mehrere Klicks auf „Stop generation“ wurden von T3 Code angenommen, erreichten Codex aber mit der falschen Turn-ID.

Status: Fehler bestätigt Datum: 25. Juli 2026 Zeitzone: Europe/Berlin Bereich: Codex · Steer · Interrupt

Kurzfassung

Das Stoppen scheiterte an einer falschen internen Turn-ID

Der Klick selbst funktionierte. T3 Code nahm jeden Stop-Befehl an und erzeugte jeweils ein thread.turn-interrupt-requested-Ereignis. Nach einer während des laufenden Turns gesendeten Nachsteuerung hatte die lokale Steer-Implementierung jedoch eine andere Turn-ID als aktiv gespeichert, obwohl beim Provider weiterhin der ursprüngliche Turn lief. Der Interrupt zielte dadurch auf den falschen Turn und wurde abgelehnt.

16 eindeutige Stop-Befehle innerhalb von rund 17 Sekunden
16 vom T3-Orchestrator angenommene Commands ohne Receipt-Fehler
0 erfolgreiche Provider-Interrupts in diesem Zeitraum
1 reproduzierbarer ID-Mismatch als gemeinsame Ursache
Verdikt: Dies war kein Bedienfehler und kein verlorener Mausklick. Es ist ein echter Zustands-/Kompatibilitätsfehler im T3-Code-Pfad für turn/steer und turn/interrupt.

Codepfad

Die problematischen Übergaben im Repository

1. Steer überschreibt die aktive ID

In apps/server/src/provider/Layers/CodexSessionRuntime.ts:1309–1324 wird bei einem laufenden Turn turn/steer aufgerufen. Anschließend setzt T3 Code session.activeTurnId ungeprüft auf response.turnId.

Diese Logik stammt aus dem lokalen Fork-Commit 883b95ebae („Feature: add queued and steered messages“).

2. Interrupt liest den überschriebenen Wert

In derselben Datei, Zeilen 1362–1373, nimmt interruptTurn ohne explizite Provider-Turn-ID den Wert aus session.activeTurnId. Dadurch wird genau die falsche ID versendet.

3. Der Event-Payload wird nicht verwendet

ProviderCommandReactor.ts:887–908 erhält zwar das thread.turn-interrupt-requested-Ereignis, ruft den Provider aber absichtlich nur per Thread/Session auf. Der Runtime-Zustand entscheidet somit allein über das Ziel.

4. Die Oberfläche sieht nur „angenommen“

ChatView.tsx:4858–4871 zeigt nur einen Fehler, wenn bereits das Dispatching des Commands scheitert. Hier war das Dispatching erfolgreich; der spätere Provider-Fehler wurde lediglich im Server-Trace protokolliert. Deshalb wirkte der Button ohne Rückmeldung.

Protokollerwartung: Laut offizieller Codex-App-Server-Dokumentation fügt turn/steer Eingabe in den aktiven Turn ein und gibt dessen aktive turnId zurück. turn/interrupt soll den laufenden Turn beenden und anschließend ein turn/completed mit Status interrupted auslösen. Der beobachtete abweichende Rückgabewert muss deshalb validiert oder robust abgefangen werden.

Abgrenzung

Was nicht die Ursache war

Nicht Google Chrome

Chrome und Browser Use waren der Arbeitskontext. Der eigentliche Fehler trat erst bei der Auswahl der Turn-ID im T3-Server auf.

Nicht der einzelne Klick

16 verschiedene Commands belegen, dass Interaktion und WebSocket-Übertragung funktionierten.

Nicht primär tab-spezifisch

Der fehlerhafte Zustand lag in der gemeinsamen Provider-Session. Ein anderer UI-Tab hätte ihn wiederverwendet.

Keine Abo-Änderung

Die Untersuchung und der ursprüngliche Turn führten keine Änderung am ChatGPT-Abonnement aus.

Bis zur Reparatur

Praktischer Workaround

  1. Während eines laufenden Turns möglichst „Queue“ statt „Send now (steer)“ verwenden, wenn später zuverlässig gestoppt werden können muss.
  2. Wenn der Stop-Button nicht reagiert, eine klare Textanweisung wie „Stoppe die Arbeit jetzt und führe keine weiteren Aktionen aus“ senden.
  3. Dabei beachten: Eine Textanweisung ist kooperativ und kein technischer Interrupt. Ein bereits laufender Tool-Aufruf kann zuerst noch zu Ende laufen.
  4. Ein Reload oder Wechsel in einen anderen Tab repariert den bereits falschen serverseitigen Session-Zustand voraussichtlich nicht.

Empfohlene Reparatur

Robustheit an drei Stellen erhöhen

  1. Steer-Antwort validieren: Wenn response.turnId von der bekannten aktiven ID abweicht, darf T3 Code den laufenden Session-Zustand nicht blind überschreiben. Die aktive ID sollte beibehalten oder über thread/read bestätigt werden.
  2. Interrupt einmal sicher neu zielen: Meldet der Provider expected active turn id … but found …, kann T3 Code die tatsächlich aktive ID übernehmen und den Interrupt genau einmal wiederholen.
  3. Fehler sichtbar machen: Scheitert die asynchrone Provider-Reaktion, sollte ein provider.turn.interrupt.failed-Aktivitätseintrag und eine verständliche Meldung im Thread erscheinen.
Wichtig: Der Fix sollte nicht nur Browser Use behandeln. Die Ursache liegt im allgemeinen Steer-/Interrupt-Zustand und kann grundsätzlich bei jedem langen Turn mit einer mid-turn Nachsteuerung auftreten.

Abnahmekriterien

So sollte die Reparatur verifiziert werden

  1. Fokussierter Runtime-Test: Ein laufender Turn erhält eine Steer-Antwort mit abweichender ID; die tatsächlich aktive ID bleibt interruptierbar.
  2. Fokussierter Provider-Test: Ein ID-Mismatch beim ersten Interrupt führt zu genau einem sicheren Retry mit der gemeldeten aktiven ID.
  3. Fehlerpfad-Test: Ein endgültig fehlgeschlagener Interrupt erzeugt eine sichtbare Thread-Aktivität statt nur eines Server-Logs.
  4. Integrierter Web-Test: Langen, harmlosen Tool-Aufruf starten, Nachricht per Send now (steer) einspeisen, Stop drücken und turn/completed: interrupted nachweisen.
  5. Zweiter Tab: denselben aktiven Thread öffnen und den Stop von dort wiederholen.
  6. Browser-Use-Variante: Den Ablauf mit einem harmlosen Chrome-Ziel wiederholen, ohne Konto-, Kauf- oder Abo-Aktionen.

Testgrenzen

Was noch nicht live verifiziert wurde

Eine isolierte Mehr-Tab-Reproduktion wurde begonnen, konnte aber nicht sauber abgeschlossen werden, weil die separate T3-Preview-Automation selbst mehrfach in PreviewAutomationTimeoutError lief. Die dafür gestarteten Testserver wurden anschließend beendet und die ausschließlich dafür angelegten temporären Zustände entfernt.

Diese Einschränkung betrifft die zusätzliche UI-Reproduktion, nicht die Ursachenanalyse: Persistierte Commands, Provider-Trace, Turn-Zuordnung und Quellcodepfad belegen den ID-Mismatch bereits unabhängig davon.

Repositoryzustand zum Abschluss der Untersuchung: sauberer Arbeitsbaum; es wurden bis zu diesem Bericht keine Änderungen am Anwendungscode vorgenommen.
